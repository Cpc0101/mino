# 测试质量、缺口求助与逐条回执

适用于需求分析、数据准备、脚本调试和正式测试。目标是证明原文预期，而不是走通一个功能。工具研究、定位优化和速度提升都不能放宽结论门槛。

## 1. 先固定测试契约

从 `case_source_list → case_source_read` 的成功收据初始化工作流。逐条记录原文前置、预期、需要的账号状态/业务对象、取证方式与共享依赖；部署版本、渠道、接口文档与实际行为分别注明来源和确认状态。

- 缺信息与实测不符合预期分开。候选 URL 返回 404/400 只证明那些地址不可用，不能证明功能或协议已下线。
- 不允许把双协议一致性改为单协议稳定性、把模板更新改为读取成功、把历史验证改为新造数据后验证，仍使用原用例的 ID / source_ref 宣称通过。
- 需要改题时向用户列出具体分歧，获得决定后由原文维护入口修订，重新读取来源；不能修改锁定的旧工作流。补充探针单列 authoring，不占原文预期通过数。
- 即使字段齐全，原文映射仍要审查判定内容：登录通过、页面打开、HTTP 200 不证明通知已读同步或业务对象正确。

## 2. 查证与求助

缺口出现时先查适用来源，不要求盲目跑完所有渠道：Nexus 环境/账号/对象记忆 → 飞书 CLI 的需求、用例、接口与准备说明 → 当前 Scout 事实。飞书权限拒绝、范围截断或 CLI 不可用如实保存具体失败，不重复同一拒绝，不用截图或猜测替代正文。

记录 `事实 / 推测 / 冲突 / 未知`；事实附来源、版本、环境和证据引用。资产记忆只作线索，使用前观察确认；不把推测保存为确定的业务事实。

没有可用来源、原文存在决定结论的冲突、缺账号/历史样本/权限且不能在现有授权内准备，或调查无进展时，立即提出自包含问题：

```json
{
  "outcome": "blocked",
  "blocker": "v1_endpoint_unknown",
  "help_request": {
    "question": "请提供本环境的正式 v1 列表入口，或确认原用例是否需修订。",
    "missing": "同一账号访问 v1/v2 的可核验入口",
    "checked_sources": ["接口文档未列 v1；Scout 请求候选地址返回路由不存在"],
    "affected_units": ["CASE-002"]
  }
}
```

上面是 finish 字段示例，仍需本工作流和 attempt_id。问题立即发到可见对话，不能只存账本。暂停受影响分支，继续独立用例；等用户提供事实后另开 attempt，保留原阻塞与写入历史。

共享缺口按依赖分组处理：同一缺权限或数据不让每条依赖用例重复登录和探路。尚未执行的依赖条目标明“未执行，依赖缺口”，不伪造 Scout 执行结果，也不把其计作通过。

## 3. 账号与新老数据

正式账号来自 Nexus 已验证范围的 `account_id`。禁止临时拼邮箱、手机号、密码后称为真实账号；也禁止先编造身份再写号池使之看似可信。自动补号仅依据已配置的项目登录策略，保留创建来源和注册回执；不知道策略来源时回读配置，不擅自改为 auto。

- 新账号 0→1：注册生命周期与起始业务状态分别确认；绑定本次触发新对象的实际 ID、归属、数量变化和状态。注册完成不等于业务数据为空。
- 老账号历史验证：确认历史对象、业务/协议版本、时间与变更前状态；保留基线并在相同 account_id / 对象上比较。老账号也可能没有所需历史样本。
- 新旧兼容：必须具备对应样本，不能拿刚造的数据冒充旧版本历史。没有样本时查准备来源或问用户，不重置老账号来规避前置。
- 写结果未知：只读核对原 task/attempt 与对象，确认停止和结果后再决定恢复；不能换号、重造对象或重放未知写操作。

## 4. 观察与有限调查

优先读 Scout 当前结构化状态、变化与结果；截图只在视觉预期或结构不足时使用。页面/iframe替换、弹窗重绘、切页或对象替换后重新观察，不跨观察沿用失效节点引用；存对象 ID / 区分特征，不存长期 UI 句柄。

等待明确状态条件，成功后立即结束等待，不把固定 sleep 或 HTTP成功当业务断言。只查询所需页面/对象，避免全量盘点账号资产或重复读取大量事件。动作完成后核对业务结果，尤其是创建、领取、删除与已读操作。

调用 workflow init 可设置 `stage_time_budget_sec` 与 `total_time_budget_sec`。支持该字段的 Nexus 默认每用例每阶段300秒、总计max(1800,expected_total×120)秒，累计调查区间包括其中等待；finish 到下一次 start 之间的用户等待不计入。预算不是设备任务超时，不能据此取消真实的长流程。

- `time_budget_exhausted` 禁止开启新的超预算调查；只读核对原任务、finish、resolve仍可进行。
- `overdue_attempts` 要求可见回执与核验，不证明设备停止，不自动判失败或跳过。
- 相同缺口没有新事实不反复申请账号或整例重跑，不通过改动作文案、重建 workflow 或添加时间戳绕预算。
- 不支持这些字段的旧服务明确采用 Agent 本轮计时，不宣称服务端已强制；仍遵守求助与无进展回执。

## 5. 可见回执与结论门槛

开跑前发范围、环境、阶段、共享缺口与预算。运行中每获得一个终态立即发一条可见 Agent 进度消息（Codex 的 commentary 或所在客户端对应渠道）。没有终态且持续执行超过约60秒时，输出最近真实步骤、已耗时、正在等待什么和最近证据；没有新证据就说没有，不输出虚构进度。

新版 `task_get.observability.case_receipts` 提供稳定 `receipt_id`、用途、结果、耗时、原因和证据上下文。按 receipt_id 去重后逐条输出；同一任务的更新回执明确标“结果更新”，重跑保留新 attempt。对话压缩/中断后从记录恢复已发 ID，不能凭“查过结果”当作已经通知。旧服务没有该字段时按 task/case/device/attempt/summary_version 去重真实结果。

```text
[7/20] CASE-007 | FORMAL | PASS | 32秒
结论：本次新对象归属、数量变化和目标状态已验证。
证据：原 task / attempt / source_hash / 断言或 artifact 引用。

[8/20] CASE-008 | FORMAL | BLOCKED
缺口：未取得旧版本历史样本；已查号池记忆和准备说明。
需要用户提供：适用账号或历史对象。其他独立用例继续。
```

示例不是实际结果。`delivery.acknowledged=false` 表示工具不能确认客户端已展示；不能把返回数据、日志、报告文件或最终汇总当成逐条可见回执。

正式 PASS 必须来自原 Scout封存记录，业务预期有有效断言、原文覆盖完整、task/case/session/attempt/revision/source_hash一致。源码检查、authoring、preparation、局部通过与 Agent 自评均不替代正式验证。`UNVERIFIED`保留证据缺口；`BLOCKED`用于必要条件缺失；`SKIPPED`只用于有依据的不适用/明确排除，不用来美化缺资源；FAIL还需区分产品差异与自动化错误。

`execution_pending=true`或`status_issue`非空时不得说整批已结束。终态不等于资源已释放。阶段收敛可以包含阻塞，但报告必须列出未验证原文项；输出结果是如实交付测试质量，不是凑“全部完成”。
